# Переписывание на Kotlin и Rust

Задача владельца: переписать на Rust и Kotlin всё, что возможно. Выбор между языками — за исполнителем.
То, что переписать нельзя, не трогаем ни при каких обстоятельствах и оставляем как есть.
Работа идёт в ветке `rewrite`; `main` остаётся собираемой. Сборки «Build APK» запускает только владелец.

## Правила выбора языка

| Что | Язык | Почему |
|---|---|---|
| Логика на JVM (протоколы, парсеры, агент, эмулятор терминала) | Kotlin | то же окружение выполнения, тот же API для оставшегося Java-кода |
| Всё, что вызывает API Android (Activity, Service, View, WebView, Keystore, AccessibilityService) | Kotlin | у Rust нет SDK для этих компонентов |
| Нативные JNI-библиотеки (`termux.c`, при возможности `adb_pairing.cpp`) | Rust (`cdylib`) | есть реальное преимущество в безопасности памяти; подключается только как `.so` через JNI |
| Тесты | остаются Java, пока не переписан код, который они проверяют | пока они служат проверкой совместимости API |

## Не трогаем

- Сторонний и upstream-код: `third-party/`, `patches/`, BoringSSL, скрипты и пакеты upstream termux-packages.
- Сборка и CI: `.github/workflows/*.yml`, `bootstrap/*`, `scripts/*` (Python, shell, Node), `jitpack.yml`. Скрипты `build.gradle` остаются на Groovy: версии AGP 4.2.2 и Gradle 7.2 закреплены, менять их нельзя.
- Ресурсы и данные: XML (разметка, манифест, строки), HTML/JS/CSS в `assets/` (trustcheck и др.), шаблоны и скрипты внутри `assets/` (`*.sh`, `*.py`, `*.js`, `*.cjs`), которые запускаются в окружении Termux, а не в приложении.
- Нативные вставки X11 для контейнеров glibc/bionic (`x11/src/main/cpp`, `x11/src/bridge`): их собирают не NDK, а скрипты под цель glibc.
- Данные пользователя в `com.termux` и установленные приложения.

## Что считается проверкой этапа

1. Исходники собираются компилятором Kotlin уровня языка 1.7 (как в проекте: плагин 1.7.22, `jvmTarget 1.8`).
2. Прежние Java-тесты модуля проходят на новом коде без правок (проверка совместимости API).
3. Сравнение публичного API: `javap` оригинала из git и порта; потерянных членов нет, добавленные объяснены.
4. Сравнение строковых констант оригинала и порта по скомпилированным классам.
5. Дифференциальный прогон: один и тот же Java-код выполняется против оригинала и против порта (случайные, но воспроизводимые входы), протоколы сравниваются построчно.
   Для кода с потоками и PTY (`TerminalSession`) — сеансовый прогон: те же сценарии через настоящий PTY на оригинале и на порте, по 6 запусков каждого; сценарий, нестабильный внутри одной реализации, считается недетерминированным и переписывается (стенд не должен зависеть от гонок).
6. Сборка на телефоне в изолированном каталоге (`/data/local/tmp/agentdroid-verify`): настоящий Gradle, плагин Kotlin, компиляция `app` против новых классов. Это не заменяет «Build APK».
7. Сборка «Build APK» на ветке `rewrite` — по решению и запуску владельца.
8. Поведение на устройстве проверяет только владелец; в отчётах это всегда отдельная строка «не проверено».

Расхождения Java и Kotlin, которые уже встречались и закрыты: `trim()` (Java — символы до U+0020, Kotlin — все пробелы Юникода), `split` (Java отбрасывает хвостовые пустые элементы), `Map<String, ? extends Object>` в сигнатурах, имена `internal`-членов (`имя$main`), `@JvmStatic`/`@JvmField`/`@Throws`, методы по умолчанию интерфейсов (`-Xjvm-default=all`), проверки на `null` на границе модуля (`-Xno-param-assertions`), исключения при `null` в явных проверках Java (`ShellQuote.quote(null)` — `NullPointerException("value")`, `ExecRequest.of(null)` — `IllegalArgumentException("command is empty")`), значение `null` вместо пустой строки там, где оно доходило до вызывающего кода (`ToolCall.name` при потоке Anthropic без имени инструмента → «unknown tool: null»).

## Осознанные отличия от Java-оригинала (этап A)

- `lowercase()`/`uppercase()` в Kotlin всегда с `Locale.ROOT`; Java-оригинал в `A11yTools`, `AndroidTools`, `McpServer`, `NetConfig`, `NetScore`, `UiTools` брал локаль устройства. Различие возможно только в локалях tr/az/lt (там Java давал «İ»/«ı» и ломал, например, уровень logcat и коды клавиш); в ru-RU и en результат тот же.
- Из `AndroidTools` убрана неиспользуемая переменная (`int i = v.indexOf(" (")`), её значение нигде не читалось.
- Публичных членов оригинала не потеряно (проверка `javap`). Добавлены только: конструктор `ExecRequest.Builder(String)` (в Kotlin `internal`, в байт-коде public), константы `ProcessBackend.MAX_OUTPUT` и `ShellFiles.CHUNK`, вспомогательные `internal`-методы с суффиксом `$main`. В 7 классах (`AgentLoop`, `McpServer`, `Tools$*`, `BackendSelector`) отличаются только подстановочные знаки дженериков (`List<? extends X>` вместо `List<X>`): Java-вызовы с теми же аргументами компилируются.
- Строковые константы оригинала в классах порта все на месте, кроме объяснённых: `"true"` теперь в общем помощнике `flag()`, регулярное выражение `"\\|"` заменено разбором по символу `'|'` (`jsplit`), односимвольные литералы `char` в Kotlin — числа, а не строки.

## Проверка чувствительности сравнения (этап A)

В копию Kotlin-кода внесены 6 заведомых ошибок (регистр `\u%04X` в `Json`, `split` вместо `jsplit` в `Triggers`, смещение на единицу при усечении результата в `AgentLoop`, порог повторов в `StuckDetector`, сообщение исключения в `ShellQuote`, код ответа в `McpServer`). Сравнение поймало 5; шестая (`split` в `Triggers`) эквивалентна: пустые ключевые слова там и так пропускаются. Тесты JUnit поймали только 2 из 6 — поэтому дифференциальный прогон остаётся обязательной частью проверки каждого этапа.

## Осознанные отличия от Java-оригинала (этап B1)

- В Kotlin нет package-private: члены, которые в Java были видны только внутри пакета `com.termux.terminal` (поля `m*` эмулятора, буфера, строки и сессии, `TerminalSession.cleanupResources`, `TextStyle.encode`/`NORMAL`, `KeyHandler.getCodeFromTermcap`, `TerminalColors.parse` и др.), стали `public`; классы `JNI` и `ByteQueue` стали `public final` (в Java — package-private), у `JNI` добавилось поле `INSTANCE`. Иначе 20 прежних Java-тестов (пакет `com.termux.terminal`) пришлось бы править. Полный список — вывод сравнения `javap`.
- Потеряны только публичные конструкторы без аргументов у служебных классов `KeyHandler`, `Logger`, `TextStyle`, `WcWidth` (в Kotlin это `object`) и синтетические методы `access$NNN`; других потерь нет.
- Добавлены `CompatKt` (`jtrim`/`jsplit` — семантика `trim`/`split` из Java), классы `Companion` и анонимные классы потоков сессии.
- `Logger`: сообщение `null` по-прежнему даёт `NullPointerException` (как нативный `println` в ART) — теперь это явная проверка `logMessage`. Различие видно только в юнит-тестах с заглушкой `android.jar`, где `Log.*` ничего не бросает.
- Особенности upstream сохранены сознательно, это не ошибки порта: главный дескриптор PTY закрывается сразу после завершения процесса (непрочитанный вывод теряется), дескриптор закрывается дважды (обёртка потока и `JNI.close`), `FileDescriptor` заполняется через рефлексию (на JDK 17+ в стенде нужен `--add-opens java.base/java.io=ALL-UNNAMED`).

## Проверка чувствительности сравнения (этап B1)

- Эмулятор, 58 ручных мутантов: 56 пойманы, 2 эквивалентны по поведению. Каждый «выживший» разбирался отдельно; в стенд добавлены недостающие проверки (запрос DECXCPR, границы координат мыши, стек заголовков, порог яркости цвета, граница отложенного кадра 256 КиБ).
- Автоматические мутации операторов и констант: 105 мутантов, 7 не компилируются, 87 пойманы, 11 выжили: 4 эквивалентны (присваивание того же значения, неизвестный код SGR 11/12 и так игнорируется, начальное значение, которое перезаписывается, код журнала под константным `false`), 4 — константы (внутри одного файла они подставляются при компиляции, их проверяет сравнение значений всех 78 статических констант оригинала и порта: расхождений нет), 3 — реальные пробелы стенда (прямоугольные операции при левом поле и режиме origin; рост строки при замене широкого символа в заполненной строке; граница `Pt` у DECFRA). Под них написаны 19 759 точечных проб; теперь все три пойманы, а оригинал и порт на пробах совпадают.
- `TerminalSession` (через PTY): 9 корректных ручных мутантов, из них 4 пойманы сразу; 3 из 5 «выживших» эквивалентны (`read <= 0`, `pid > 1`, повторный `JNI.close`), 2 — пробелы (уведомление об обновлении экрана после `reset`, сброс отложенного кадра при изменении размера): добавлены сценарии, оба пойманы.
- Стенд, тесты и мутанты лежат вне репозитория (рабочий каталог исполнителя) и в коммит не входят; повторить их можно по описанию выше.

## Осознанные отличия от C-оригинала (этап B2)

- `libtermux.so` собирается из Rust (`terminal-emulator/src/main/rust`): `no_std`, без зависимостей (нужны только `core`, `alloc` и libc платформы; ни Cargo, ни crates.io, ни `libstd`), выделение памяти через `malloc`, паника — `abort`. Экспортируются те же пять функций JNI, что и в `termux.c` (`setPtyUTF8Mode`, как и раньше, Java не вызывает), и заглушка `rust_eh_personality`: при `panic=abort` она не вызывается, но без неё загрузчик отказал бы в библиотеке из-за неопределённого символа.
- Исправлено то, что в оригинале на штатных входах не проявлялось: рабочий каталог освобождался вызовом `ReleaseStringUTFChars(env, cmd, cmd_cwd)` со строкой `cmd`; при ошибке `waitpid` читалась неинициализированная переменная `status` (теперь повтор при `EINTR`, иначе результат 0 — значение ветки «не должно случаться»); при сбое `grantpt`/`unlockpt`/`ptsname_r`, `fork` и записи номера процесса главный дескриптор PTY не закрывался (теперь закрывается); `tcgetattr` не проверялся; локальные ссылки на элементы массивов аргументов и окружения копились до выхода из native-метода (теперь `DeleteLocalRef`; на ART не проверялось).
- Код дочернего процесса до `exec` сам не выделяет память и не вызывает `asprintf`/`perror`/`fflush`: тексты ошибок `chdir`/`exec` готовятся до `fork` и пишутся через `write(2)` (вызовы libc `opendir`/`putenv`/`execvp`, как и в оригинале, могут выделять память внутри). Сбой `open` slave-устройства завершает его `_exit(255)` вместо `exit(-1)` (тот же код 255, но без запуска обработчиков завершения в копии процесса JVM).
- Вызовы вне контракта, раньше — неопределённое поведение: `null` вместо команды (на терминале `exec("(null)"): No such file or directory`, код 1) или каталога (`chdir("(null)"): Bad address`), `null`/пустой массив для номера процесса и `null`-элемент в аргументах или окружении дают `RuntimeException`.
- Сохранено намеренно: тексты исключений и сообщений на терминале, усечение размеров окна до 16 бит, закрытие унаследованных дескрипторов через `/proc/self/fd`, порядок действий в дочернем процессе.
- Сборка: задача `buildTerminalNative` в `terminal-emulator/build.gradle` заменила шаг ndkBuild (`Android.mk` удалён, `termux.c` остался как запасной вариант). Режим `-PterminalNative=auto|rust|c`: по умолчанию Rust, а если его собрать нельзя (нет `rustc`, нет цели Rust и `rustup`, ошибка компоновщика), для этой архитектуры собирается `termux.c` тем же NDK-clang, и в журнале появляется `WARNING terminal-emulator [abi]` с причиной. Rust линкуется самым новым установленным NDK (в CI r27), C — NDK из `ndkVersion` (r22.1), как раньше. Строка `terminal-emulator [abi]: libtermux.so built from Rust|C (N bytes)` в журнале сборки показывает, что вошло в APK. Готовая `src/main/jniLibs/<abi>/libtermux.so` отключает задачу целиком: так делает `scripts/build-local-arm64.sh`, который по-прежнему линкует C (скрипты не трогаем).

## Проверка (этап B2)

- Один и тот же Java-код (классы Kotlin-порта `JNI`/`TerminalSession`) работает с C-библиотекой и с Rust-библиотекой; результаты сравниваются построчно: прямые вызовы `JNI` (39 общих случаев: аргументы, окружение, каталог, размеры окна и их усечение, флаги терминала, коды выхода и сигналы, UTF-8 в аргументах и окружении, 3000 аргументов, `E2BIG`, утечка дескрипторов, параллельный запуск, плюс 7 случаев только для Rust), нативный драйвер без JVM (`setPtyUTF8Mode`, неверные дескрипторы, `waitFor`), исчерпание дескрипторов, `-Xcheck:jni` (без предупреждений), 45 сеансовых сценариев `TerminalSession` через настоящий PTY. Прогонялось на хосте (glibc, JDK 21) и на телефоне (Bionic aarch64, Android 14, OpenJDK 17, Termux rustc/clang, классы Kotlin собраны там же плагином 1.7.22): расхождений C и Rust нет.
- Сборка Gradle на телефоне (Gradle 7.6.4, AGP 4.2.2): `:terminal-emulator:assembleDebug` с настоящей задачей; «NDK» — обёртки над clang из Termux (настоящий NDK на телефоне не запускается). Задача выполняется перед `mergeDebugJniLibFolders`, AAR содержит `jni/arm64-v8a/libtermux.so`, и эта библиотека (после `strip` в AGP) проходит тот же стенд с теми же результатами. Режимы: только C; авто с намеренно сломанным компоновщиком Rust (предупреждение с причиной, на выходе байт-в-байт та же библиотека, что в режиме только C); только Rust со сломанным компоновщиком (сборка падает с ясной ошибкой); после починки — снова Rust.
- Логика задачи на обычном Gradle 8.14.3 в песочнице с подставными NDK: путь Rust, откат на C, «только Rust» без цели (ошибка с причиной от `rustup`), «только C», готовая библиотека в `jniLibs` (задача пропускается), выбор NDK (Rust — новейший, C — закреплённый), неверные значения свойств, нет обёртки clang, повторный запуск (UP-TO-DATE).
- Компиляция Rust до объектного файла для всех четырёх целей (`aarch64-linux-android`, `armv7-linux-androideabi`, `i686-linux-android`, `x86_64-linux-android`); линковка — только arm64 (на телефоне цели 32-бит ARM, x86 и x86_64 доступны Termux-rustc лишь как метаданные).
- Не проверено: линковка настоящим NDK (r22.1/r27, clang + lld) и установка целей Rust через `rustup` на раннере GitHub; загрузка библиотеки в ART и работа терминала в приложении; «Build APK» на ветке `rewrite`.

## Осознанные отличия от Java-оригинала (этап B3)

- В Kotlin нет package-private: члены, которые в Java были видны только внутри пакета `com.termux.view`, стали `private` (поля `mTopRow`, `mDefaultSelectors`, `mScaleFactor`, `mGestureRecognizer`, `mScroller`, `mScrollRemainder`, `mCombiningAccent` у `TerminalView`; методы `sendMouseEventCode`, `doScroll`, `getTextSelectionCursorController`, `hideFloatingToolbar`; `mListener` и `isAfterLongPress` у `GestureAndScaleRecognizer`; `mTempCoords` и `mTempRect` у `TextSelectionHandleView`). Других пользователей в репозитории нет (проверено поиском по всему дереву).
- Поля `TerminalRenderer` `mTextSize`, `mTypeface`, `mFontWidth`, `mFontLineSpacing`, `mFontLineSpacingAndAscent` (package-private final в Java) — `@JvmField internal`, то есть public final в байт-коде, с теми же именами: их находит рефлексия прежних тестов (`OpenCodeResizeTest`, `GeminiScrollTest`).
- `GestureAndScaleRecognizer` — `internal` (в байт-коде public; в Java был package-private). `TextSelectionCursorController` и `TextSelectionHandleView` — `final` (в Java — public без `final`); наследников в репозитории нет.
- `TextSelectionCursorController.ACTION_COPY/PASTE/MORE` (в Java — `public final int` экземпляра, подставлялись в `case`) — `@JvmField val`, а `switch` — `when` по ним; значения 1/2/3 те же.
- Удалено приватное поле `TerminalView.mCursorInvisibleIgnoreOnce`: в Java оно нигде не читалось и не записывалось.
- `null`: там, где Java разыменовал бы значение без проверки, стоит `!!` (то же `NullPointerException`); нигде нет `?.` и `?:`. Приведения `getSystemService(...) as AccessibilityManager` / `as ClipboardManager` при `null` бросают исключение на строку раньше, чем Java на разыменовании; на практике служба всегда есть. Для вызовов `x!!.f(args)` аргументы не вычисляются, если `x == null` (Java сначала вычисляет аргументы, потом бросает), но аргументы во всех таких местах без побочных эффектов.
- Интерфейс `TerminalViewClient` — методы по умолчанию как настоящие JVM-методы (`-Xjvm-default=all`), Java-реализации (`TermuxTerminalViewClient` и др.) компилируются без правок.

## Осознанные отличия от Java-оригинала (этап B4)

- Соглашения те же, что в B1 и B3: `getX()`/`setX()` остались методами, а не свойствами; `@JvmField`, `@JvmStatic`, `@Throws`; `-Xjvm-default=all`; проверки `null` у параметров и вызовов выключены (`-Xno-param-assertions`, `-Xno-call-assertions`, `-Xno-receiver-assertions`). Исходники лежат в `termux-shared/src/main/kotlin`; в `build.gradle` подключён плагин Kotlin (версия берётся из `buildscript` корневого проекта, 1.7.22), `sourceJar` включает и каталог Kotlin. На Java в модуле остался только инструментальный тест-заглушка `src/androidTest/.../ExampleInstrumentedTest.java`.
- 52 класса, где были только статические члены (`FileUtils`, `Logger`, `ShellUtils`, `TermuxConstants` и его вложенные классы констант и т. п.), — Kotlin `object` с `@JvmStatic`/`@JvmField`/`const`. Для Java-кода `Foo.bar()` и константы выглядят как прежде; в байт-коде добавилось поле `INSTANCE`, 50 из них потеряли неявный публичный конструктор без аргументов, все стали `final`. `new Foo()` для них, наследников и подмен (`mock`/`spy`; Mockito в репозитории нет) нет нигде в `.java` и `.kt` репозитория (проверено поиском).
- 34 вложенных класса `Companion` — у классов, где рядом со статическими членами есть экземпляры; обращения из Java прежние. 14 синтетических конструкторов с `DefaultConstructorMarker` Kotlin создаёт сам для закрытых конструкторов; видны только через рефлексию.
- В Kotlin нет package-private: 67 членов, видимых в Java только внутри пакета, стали `public` (49 полей `UnixConstants`, 5 полей `SpecialButtonState`, конструкторы `FileKey`, `FileUtils.ReadSerializableObjectResult`, `FileUtilsErrno`, `FunctionErrno`, `ResultSenderErrno`, `ReflectionUtils.FieldInvokeResult` и `MethodInvokeResult`, `ReportActivity.NewInstanceResult`, `CleverMap` (конструктор, `get(K, V)`), `StreamGobbler.conditionalJoin`, `ExtraKeysView.showPopup` и `maximumLength`); класс `ExtraKeysConstants.CleverMap` стал `public`. Сужений видимости нет. Значения всех констант оригинала в порте на месте (сравнение `javap -constants`: расхождение только у трёх полей `UnixConstants` — видимость).
- У `TermuxTask` методы `getExecutionCommand`, `getProcess`, `kill`, `killIfExecuting` стали `final` (в Java переопределяемые); наследников в репозитории нет.
- `CleverMap` (наследник `HashMap`) и `ExtraKeyDisplayMap` получили служебные методы, которые Kotlin добавляет наследникам `Map` (`getSize()`, `getKeys()`, `getValues()`, `getEntries()`, перегрузки `get`/`containsKey`/`remove`/`getOrDefault` для `String`); вызовы из Java разрешаются так же.
- Вызов Java-метода с переменным числом аргументов, которому явно передан `null` вместо массива (`Errno.getError(..., (Object[]) null)`, методы `ReflectionUtils`): Kotlin при передаче `*args` бросает `NullPointerException`, Java передавала `null` дальше. В репозитории таких вызовов нет.
- Имена анонимных классов другие: Kotlin называет их по объемлющему объявлению (`ExtraKeysConstants$EXTRA_KEY_DISPLAY_MAPS$DEFAULT_CHAR_DISPLAY$1` вместо `ExtraKeysConstants$EXTRA_KEY_DISPLAY_MAPS$1`); заметно только через `getClass().getName()` и по размеру сериализованной формы этих константных словарей. Именованные классы совпадают: по 114 в оригинале и в порте.
- `ExtraKeysView`: в Java-версии при компиляции против урезанного `android.jar` появляются мостовые методы `generateDefaultLayoutParams`, `generateLayoutParams` и `getOverlay` (их `javac` добавляет, потому что в заглушках SDK нет мостов `GridLayout`); в Kotlin-версии их нет. Это артефакт сборки, на настоящем Android мосты есть в самом `GridLayout`.
- `null`: нигде нет `?.` и `?:`; там, где Java разыменовала бы значение, стоит `!!` (то же `NullPointerException`); `Any?.toString()`/`equals`/`hashCode()` на nullable-получателе нигде не вызываются (пробная компиляция с «ядовитыми» расширениями, см. ниже). Приведение `(T) x`, где Java допускала `null`, записано как `as T?`; единственное такое место, найденное разбором файлов вне стенда (`TextIOActivity`: `getParent() as ViewGroup?`, дальше в Java идёт проверка `parent != null`), исправлено вручную. Для вызовов `x!!.f(args)` аргументы не вычисляются, если `x == null` (Java сначала вычисляет аргументы, потом бросает): порядок побочных эффектов различается только на пути, где в обоих вариантах всё равно исключение.
- Сериализация: приложение сериализует только `ReportInfo` и `TextIOInfo` (`putSerializable` в `Bundle` и `onSaveInstanceState`; `ReportInfo` ещё записывается в файл `FileUtils.writeSerializableObjectToFile` и читается обратно). У обоих остался явный `serialVersionUID = 1L`, как в оригинале. Проверено в песочнице на уровне JVM (`ObjectOutputStream`/`ObjectInputStream`, не настоящий `Bundle`): дескрипторы потока (UID, набор полей, суперкласс) оригинала и порта совпадают; объект, записанный оригиналом, читается портом и наоборот, значения полей равны (`ReportInfo` со всеми полями и с `null`, `TextIOInfo` с изменёнными значениями и по умолчанию); потоки `TextIOInfo` побайтно совпадают, у `ReportInfo` отличаются только цифры метки времени. У `ResultData` и `Error` явного UID нет, вычисляемый UID порта другой: объект одной сборки другой не читается (`InvalidClassException` в обе стороны). В репозитории они нигде не сериализуются: `putSerializable` и запись в файл получают только `ReportInfo`/`TextIOInfo`, а `DataUtils.getSerializedSize` вызывается один раз — для `ReportInfo`.
- Комментарии: все 902 документирующих блока `/** */` перенесены. 29 обычных комментариев в позициях, которые конвертер не переносит (между ветками `else`, `/* boolean */`-пометки в `TermuxPropertyConstants` и `TermuxSharedProperties`, закомментированный код, пояснение к `canExecute()` в `FileUtils`), потеряны; их текст есть в истории git (`git show 155fc89:termux-shared/src/main/java/...`).
- После конвертера внесено 11 ручных правок в 7 файлах (`TermuxSession`: приведение массива аргументов; `ExtraKeyButton`: тип функции `Function<String?, String?>`; `ExtraKeysView`: 5 мест — `String::new`, `Map.Entry::key/value`, тип матрицы кнопок; `ReportActivity`: `setMarkdown(markwon, x!!)`, параметр Markwon помечен `@NonNull`; `SharedProperties`: `map.inverse().get(x as Any?)`; `ViewUtils`: `windowMetrics.bounds`, `androidx.window` написана на Kotlin; `TextIOActivity`: приведение `getParent()`). Три из них (`ReportActivity`, `SharedProperties`, `ViewUtils`) вызваны ошибками, которые видит только настоящая сборка на телефоне: песочнице неизвестны `@NonNull` сторонних библиотек и библиотеки на Kotlin.
