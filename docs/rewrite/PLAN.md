# Переписывание на Kotlin и Rust

Задача владельца: переписать на Rust и Kotlin всё, что возможно. Выбор между языками — за исполнителем.
То, что переписать нельзя, не трогаем ни при каких обстоятельствах и оставляем как есть.
Работа идёт в ветке `rewrite`; `main` остаётся собираемой. Сборки «Build APK» запускает только владелец.

## Правила выбора языка

| Что | Язык | Почему |
|---|---|---|
| Логика на JVM (протоколы, парсеры, агент, эмулятор терминала) | Kotlin | то же окружение выполнения, тот же API для оставшегося Java-кода |
| Всё, что вызывает API Android (Activity, Service, View, WebView, Keystore, AccessibilityService) | Kotlin | у Rust нет SDK для этих компонентов |
| Нативные JNI-библиотеки (`termux.c`, при возможности `adb_pairing.cpp`) | Rust (`cdylib`) | есть реальное преимущество в безопасности памяти; подключается только как `.so` через JNI |
| Тесты | остаются Java, пока не переписан код, который они проверяют | пока они служат проверкой совместимости API |

## Не трогаем

- Сторонний и upstream-код: `third-party/`, `patches/`, BoringSSL, скрипты и пакеты upstream termux-packages.
- Сборка и CI: `.github/workflows/*.yml`, `bootstrap/*`, `scripts/*` (Python, shell, Node), `jitpack.yml`. Скрипты `build.gradle` остаются на Groovy: версии AGP 4.2.2 и Gradle 7.2 закреплены, менять их нельзя.
- Ресурсы и данные: XML (разметка, манифест, строки), HTML/JS/CSS в `assets/` (trustcheck и др.), шаблоны и скрипты внутри `assets/` (`*.sh`, `*.py`, `*.js`, `*.cjs`), которые запускаются в окружении Termux, а не в приложении.
- Нативные вставки X11 для контейнеров glibc/bionic (`x11/src/main/cpp`, `x11/src/bridge`): их собирают не NDK, а скрипты под цель glibc.
- Данные пользователя в `com.termux` и установленные приложения.

## Что считается проверкой этапа

1. Исходники собираются компилятором Kotlin уровня языка 1.7 (как в проекте: плагин 1.7.22, `jvmTarget 1.8`).
2. Прежние Java-тесты модуля проходят на новом коде без правок (проверка совместимости API).
3. Сравнение публичного API: `javap` оригинала из git и порта; потерянных членов нет, добавленные объяснены.
4. Сравнение строковых констант оригинала и порта по скомпилированным классам.
5. Дифференциальный прогон: один и тот же Java-код выполняется против оригинала и против порта (случайные, но воспроизводимые входы), протоколы сравниваются построчно.
   Для кода с потоками и PTY (`TerminalSession`) — сеансовый прогон: те же сценарии через настоящий PTY на оригинале и на порте, по 6 запусков каждого; сценарий, нестабильный внутри одной реализации, считается недетерминированным и переписывается (стенд не должен зависеть от гонок).
6. Сборка на телефоне в изолированном каталоге (`/data/local/tmp/agentdroid-verify`): настоящий Gradle, плагин Kotlin, компиляция `app` против новых классов. Это не заменяет «Build APK».
7. Сборка «Build APK» на ветке `rewrite` — по решению и запуску владельца.
8. Поведение на устройстве проверяет только владелец; в отчётах это всегда отдельная строка «не проверено».

Расхождения Java и Kotlin, которые уже встречались и закрыты: `trim()` (Java — символы до U+0020, Kotlin — все пробелы Юникода), `split` (Java отбрасывает хвостовые пустые элементы), `Map<String, ? extends Object>` в сигнатурах, имена `internal`-членов (`имя$main`), `@JvmStatic`/`@JvmField`/`@Throws`, методы по умолчанию интерфейсов (`-Xjvm-default=all`), проверки на `null` на границе модуля (`-Xno-param-assertions`), исключения при `null` в явных проверках Java (`ShellQuote.quote(null)` — `NullPointerException("value")`, `ExecRequest.of(null)` — `IllegalArgumentException("command is empty")`), значение `null` вместо пустой строки там, где оно доходило до вызывающего кода (`ToolCall.name` при потоке Anthropic без имени инструмента → «unknown tool: null»).

## Осознанные отличия от Java-оригинала (этап A)

- `lowercase()`/`uppercase()` в Kotlin всегда с `Locale.ROOT`; Java-оригинал в `A11yTools`, `AndroidTools`, `McpServer`, `NetConfig`, `NetScore`, `UiTools` брал локаль устройства. Различие возможно только в локалях tr/az/lt (там Java давал «İ»/«ı» и ломал, например, уровень logcat и коды клавиш); в ru-RU и en результат тот же.
- Из `AndroidTools` убрана неиспользуемая переменная (`int i = v.indexOf(" (")`), её значение нигде не читалось.
- Публичных членов оригинала не потеряно (проверка `javap`). Добавлены только: конструктор `ExecRequest.Builder(String)` (в Kotlin `internal`, в байт-коде public), константы `ProcessBackend.MAX_OUTPUT` и `ShellFiles.CHUNK`, вспомогательные `internal`-методы с суффиксом `$main`. В 7 классах (`AgentLoop`, `McpServer`, `Tools$*`, `BackendSelector`) отличаются только подстановочные знаки дженериков (`List<? extends X>` вместо `List<X>`): Java-вызовы с теми же аргументами компилируются.
- Строковые константы оригинала в классах порта все на месте, кроме объяснённых: `"true"` теперь в общем помощнике `flag()`, регулярное выражение `"\\|"` заменено разбором по символу `'|'` (`jsplit`), односимвольные литералы `char` в Kotlin — числа, а не строки.

## Проверка чувствительности сравнения (этап A)

В копию Kotlin-кода внесены 6 заведомых ошибок (регистр `\u%04X` в `Json`, `split` вместо `jsplit` в `Triggers`, смещение на единицу при усечении результата в `AgentLoop`, порог повторов в `StuckDetector`, сообщение исключения в `ShellQuote`, код ответа в `McpServer`). Сравнение поймало 5; шестая (`split` в `Triggers`) эквивалентна: пустые ключевые слова там и так пропускаются. Тесты JUnit поймали только 2 из 6 — поэтому дифференциальный прогон остаётся обязательной частью проверки каждого этапа.

## Осознанные отличия от Java-оригинала (этап B1)

- В Kotlin нет package-private: члены, которые в Java были видны только внутри пакета `com.termux.terminal` (поля `m*` эмулятора, буфера, строки и сессии, `TerminalSession.cleanupResources`, `TextStyle.encode`/`NORMAL`, `KeyHandler.getCodeFromTermcap`, `TerminalColors.parse` и др.), стали `public`; классы `JNI` и `ByteQueue` стали `public final` (в Java — package-private), у `JNI` добавилось поле `INSTANCE`. Иначе 20 прежних Java-тестов (пакет `com.termux.terminal`) пришлось бы править. Полный список — вывод сравнения `javap`.
- Потеряны только публичные конструкторы без аргументов у служебных классов `KeyHandler`, `Logger`, `TextStyle`, `WcWidth` (в Kotlin это `object`) и синтетические методы `access$NNN`; других потерь нет.
- Добавлены `CompatKt` (`jtrim`/`jsplit` — семантика `trim`/`split` из Java), классы `Companion` и анонимные классы потоков сессии.
- `Logger`: сообщение `null` по-прежнему даёт `NullPointerException` (как нативный `println` в ART) — теперь это явная проверка `logMessage`. Различие видно только в юнит-тестах с заглушкой `android.jar`, где `Log.*` ничего не бросает.
- Особенности upstream сохранены сознательно, это не ошибки порта: главный дескриптор PTY закрывается сразу после завершения процесса (непрочитанный вывод теряется), дескриптор закрывается дважды (обёртка потока и `JNI.close`), `FileDescriptor` заполняется через рефлексию (на JDK 17+ в стенде нужен `--add-opens java.base/java.io=ALL-UNNAMED`).

## Проверка чувствительности сравнения (этап B1)

- Эмулятор, 58 ручных мутантов: 56 пойманы, 2 эквивалентны по поведению. Каждый «выживший» разбирался отдельно; в стенд добавлены недостающие проверки (запрос DECXCPR, границы координат мыши, стек заголовков, порог яркости цвета, граница отложенного кадра 256 КиБ).
- Автоматические мутации операторов и констант: 105 мутантов, 7 не компилируются, 87 пойманы, 11 выжили: 4 эквивалентны (присваивание того же значения, неизвестный код SGR 11/12 и так игнорируется, начальное значение, которое перезаписывается, код журнала под константным `false`), 4 — константы (внутри одного файла они подставляются при компиляции, их проверяет сравнение значений всех 78 статических констант оригинала и порта: расхождений нет), 3 — реальные пробелы стенда (прямоугольные операции при левом поле и режиме origin; рост строки при замене широкого символа в заполненной строке; граница `Pt` у DECFRA). Под них написаны 19 759 точечных проб; теперь все три пойманы, а оригинал и порт на пробах совпадают.
- `TerminalSession` (через PTY): 9 корректных ручных мутантов, из них 4 пойманы сразу; 3 из 5 «выживших» эквивалентны (`read <= 0`, `pid > 1`, повторный `JNI.close`), 2 — пробелы (уведомление об обновлении экрана после `reset`, сброс отложенного кадра при изменении размера): добавлены сценарии, оба пойманы.
- Стенд, тесты и мутанты лежат вне репозитория (рабочий каталог исполнителя) и в коммит не входят; повторить их можно по описанию выше.
